Troubleshooting

Common issues encountered while configuring, running, or contributing to the Patrol Grid Visit Workflow, and how to resolve them. If your issue isn't listed here, open an issue on GitHub.

Configuration & Connections

No data returned from EarthRanger for get_patrol_observations_with_patrol_filter

No completed patrols with tracks matched your settings. Check that:

  • The Time Range covers a period when patrols were recorded.
  • The patrols are marked done in EarthRanger. Active, scheduled, and cancelled patrols are not fetched.
  • Each Patrol Types value exactly matches a patrol type value in EarthRanger. Leave the field empty to include every type.

EarthRanger connection fails or times out

Verify the server URL and credentials configured in the EarthRanger connection (see Data Source Connection). Confirm you can log into that same EarthRanger instance in a browser with the same account, and that the account has permission to view patrols.

Basemap tiles don't load, or the background map is blank

The Base Map Layers are user-editable. If you changed them away from the ArcGIS defaults, confirm each tile URL follows the standard {z}/{y}/{x} template and is reachable from the machine running the workflow.

Map Outputs

The map is empty or very sparse, even though patrols exist

The default Segment Filter is permissive and keeps almost every segment, so check whether it has been tightened. Limits such as max 9 km/h or 5 km per segment suit foot patrols but discard most vehicle, motorbike, or aerial patrol segments. Patrol tracks with only one GPS fix cannot form a segment and are always excluded.

Straight lines of visited cells cut across areas nobody patrolled

These come from GPS gaps. When a device loses signal or is switched off, the segment joining the fixes on either side of the gap is a straight line, and every cell it crosses is credited with a visit. The default Segment Filter keeps segments up to 100 km and 48 hours long. Lower Max Length Meters and Max Time Secs (e.g. 5000 and 21600 for foot patrols) to drop them.

Almost every cell is in the lowest color bin

The 5 bins are equal-width ranges between the least- and most-visited cells. One or two very busy cells (for example next to a ranger post or along a main road) stretch the range so that everything else falls into the first bin. A larger Grid Cell Size can smooth this out. To change the classification scheme (e.g. to quantile or natural_breaks), edit classification_options in spec.yaml and recompile.

The grid looks too blocky, or too fine to read

Adjust Grid Cell Size. The default 1000 gives roughly 1 km cells near the equator. The grid is built in Web Mercator (EPSG:3857), so cells cover slightly less ground the further you are from the equator (about 6 % smaller at 20°).

ValueError: Missing required columns: ['patrol_id'] ...

The coverage grid needs a patrol_id column on every trajectory segment. It is produced by the Map Columns step, which renames extra__patrol_id to patrol_id. If you edited spec.yaml, make sure patrol_id is still listed in relocs_columns under Process Relocations and that the rename is still in place.

No outputs written / can't find results

All outputs are written to the directory specified by the ECOSCOPE_WORKFLOWS_RESULTS environment variable. Confirm it's set and points to a directory the workflow process can write to.

Contributing & CI

These apply if you're modifying the workflow itself (spec.yaml or the generated ecoscope-workflows-patrol-grid-visit-workflow/ directory) and opening a pull request.

Compiled artifact 'params.json' is not a valid JSON Schema: 'ecoscope.platform.annotations.DataFrame' is not valid under any of the given schemas

A task in spec.yaml has a DataFrame/GeoDataFrame parameter that isn't set in its partial block, so the compiler tries to expose it as a form field, which isn't possible. The error's path names the task and parameter (e.g. reloc_coord_filter → roi_gdf). Set that parameter in partial, either to null or to an upstream result such as ${{ workflow.<id>.return }}, and recompile. This often appears after a package upgrade adds a new optional parameter to an existing task.

ValidationError: ... label_options.DefaultLabels.label_prefix Input should be a valid string [... input_value=None ...]

The compiler writes None for any label_options field the spec leaves out, and apply_classification rejects it. Set every label field explicitly under the Apply Classification task:

label_options:
  label_prefix: ""
  label_suffix: ""
  label_ranges: true
  label_decimals: 0

Generated files differ from committed files in ecoscope-workflows-patrol-grid-visit-workflow

The generated workflow directory is out of sync with spec.yaml. Run the recompile script locally and commit the result:

pixi run --manifest-path pixi.toml --locked bash -c "./dev/recompile.sh --update"

Found wildcard version (*) in requirements or Found local file channel (file://) in requirements

In spec.yaml, every dependency under requirements must pin a version and use a remote conda channel. Wildcard versions and local file:// channels are only valid for local development.

VERSION.yaml (...) must be greater than main branch (...)

Bump MAJ/MIN/PATCH in ecoscope-workflows-patrol-grid-visit-workflow/VERSION.yaml so it's strictly greater than the version on main before opening or updating a PR.

test-cases.yaml must contain at least one test case

Every workflow requires a test-cases.yaml at the repository root with at least one top-level entry containing a params block. Use the settings from a successful run as the starting point.
